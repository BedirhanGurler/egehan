# Conformance fixtures

Egehan ships two engines — Node and .NET — and intends to be portable to more. "The two engines agree"
is the project's core correctness claim, and these fixtures are how that claim is *proved* rather than
promised.

## How a fixture works

```text
01-frontend-saas/
├── input.json              # a synthetic, already-parsed commit history (fixture-input.schema.json)
├── expected.tr.poetic.json # the report the engine must produce, byte for byte
├── expected.en.minimalist.json
└── …                       # one expected file per (language, tone) pair under test
```

Every engine's test suite loads `input.json`, runs its story engine over it, and compares the result to
the matching `expected.*.json` with `generator.generatedAt` excluded — that is the one field allowed to
depend on wall-clock time. Any other difference is a conformance failure, whichever engine produced it.

## Why the input starts after git

`input.json` is the normalized commit list, not raw `git log` output. That is the documented boundary in
the architecture: reading git is platform-specific plumbing (process spawning, encodings, path quoting),
while classification, narration and statistics must be identical everywhere. Fixtures test the half that
must not drift. The git-reading half is covered by each engine's own tests against real throwaway
repositories.

## Regenerating the expected files

Expected reports are generated by the reference engine and then reviewed by a human — they are never
hand-written, because a hand-written expectation is just a second implementation with no tests:

```bash
npm run fixtures:generate -w egehan     # writes expected.*.json for every fixture
git diff -- packages/core-spec/fixtures # review every changed sentence before committing
```

A change to `spec/rules.json` or to a dictionary is *supposed* to move these files. Reviewing that diff
is the moment you find out whether the rule change said what you meant.

## Adding a fixture

Cover a behaviour the existing fixtures do not. Keep histories small and legible — a fixture that nobody
can read by eye cannot be reviewed, and an unreviewable expectation protects nothing. Use realistic
timezone offsets: the local hour is what makes `midnight-oil` mean anything, so a fixture written entirely
in UTC exercises the least interesting case.
